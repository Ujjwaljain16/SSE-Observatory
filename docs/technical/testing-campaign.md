# Testing campaign

What has been tested beyond the ordinary unit and end-to-end tests, what it found, what is still open, and what has not been done. **Status: the campaign ended with the release of v2.0.0 on 2026-11-15**; every decision it raised was taken by the owner and is implemented (the table under "Owner decisions"), and the release gate is under "Release readiness". After the release, the deployed site is checked end to end with `npm run smoke:live`. Every claim here can be checked with the command or the file named next to it.

The campaign's idea: more tests of the same shape find few bugs, so it uses **independent oracles** (the WHATWG algorithm written out literally, the fixture server's own log, a strict XML parser, the specification's own examples), **real processes** (the built command line), and **tables that pin every threshold at its edge**. Each defect gets a failing test before its fix.

## Open decisions

The sections below are the questions as they were put, each pinned by a test so the behaviour is visible. The decisions are in the table above. Q4a and Q4b are decided and done: see "Decided and implemented" below.

### Q-I1. The capture to share is documented as replayable by the command line, and the command line refused it (decided and done)

`docs/guide/stream-doctor.md` says the capture to share "can be analysed and replayed" by the command line. `sse-doctor replay` used to refuse it (exit 2, "holds no payload to replay"), because the app records what happened on the wire and not what events said; the app's own **Replay in Mock mode** button first made a labelled copy with placeholder bodies, and the command line did not.

**Decision (the owner):** the command line replays it, matching the app, as a synthetic replay and not a byte-exact one. Done: the app's `replayCopy` moved to `src/core/capture/replayCopy.ts` (one function for both), and `src/cli/replaySource.ts` builds the copy in memory for `replay`. Ids, event names, order and times are kept; each body is a placeholder of the recorded size (an event with no recorded size gets the smallest valid body, and the notice counts them); the notice on stderr, the address line and an `X-Mock-Synthetic` response header say it is synthetic; the file is never changed or written to. A capture that holds payload replays exactly as before, unlabelled. Still refused (exit 2, with the reason): a capture with no events, with no recorded event size at all, with sizes that add up to more than 16 MB, and a damaged file. Tests: `src/cli/__tests__/replaySynthetic.test.ts`, `src/core/capture/__tests__/replayCopy.test.ts`, and the journey step 5a, which now replays the downloaded file.

**Left open:** a scenario's `target.replay` that names such a capture (`sse-doctor test`) is still refused, because `src/cli/scenarioRunner.ts` calls the mock's session reader directly; it can call `loadReplaySession` from `src/cli/replaySource.ts` and add a label to its output (the `test` JSON schema would need an optional field). The copy keeps events only, so comments and heartbeats in the recording are not replayed, and a recorded size of 3 to 6 bytes becomes 7 (the shortest padded body).

### Q-I2. A scenario's `reconnect` step did not delay the connection or drop the cursor after a server drop (DECIDED and done; the lead moves it to "Decided and done")

`docs/guide/cli-ci.md`: "`reconnect` waits `after_ms`, then connects again; `resume_from_last_event_id: false` forgets the cursor first." After `disconnect: server` the runner's client had already reconnected, with the cursor, within about 20 ms, so neither was honoured (defect 19 only fixed the counting).

**Decided by the owner, done:** runner-controlled reconnects for explicit `reconnect` steps, honouring `after_ms` and `resume_from_last_event_id: false`, and a separate automatic-reconnect path kept for testing the client's real reconnection. A scenario that has a `reconnect` step holds its client at the drop of an open connection (the client is stopped as it starts to reconnect), and the step is the reconnect: it waits `after_ms` from the moment it runs, forgets the cursor if told to, and connects. A `reconnect` step with no drop before it closes the open connection first. A scenario with no `reconnect` step is unchanged: the client reconnects by itself, with the cursor, and that is what it tests. The consequence: in a scenario with a `reconnect` step, a collect step that asks for more events than the connection sent before the server dropped it now fails at once ("the server dropped the connection after N") instead of counting events across the drop. The schema did not change. ### Q12. A stall that ended with a closed connection stays open after a healthy reconnect: decided and implemented

The stall finding was `resolved` only when data resumed on the same connection. A silence that ended because the connection closed stayed `open`, even after the client reconnected and the new connection was healthy; exit-code gates and the Doctor's open counts read `open`.

**The owner's decision:** "Resolve the active stall finding when a subsequent connection successfully delivers an event. Preserve the original stall as historical evidence, including its duration, connection and occurrence count. A recovered stream should not continue failing an active-health gate just because an earlier connection experienced a stall."

**Implemented:** R05 (`stall.silent`), R13 (`proxy.masking`) and R04 (`timing.first-event`, a stage that never completed because its connection ended) now resolve when a later connection delivers an event (for R04, completes that stage within its limit). The finding keeps every fact, number and the evidence of the stall and gains one fact, with evidence pointing at the event that ended it. A later connection that has delivered nothing, or only heartbeats, does not resolve it; a capture that ends in a stall still has it open; a new silence after a recovery reopens it with the count raised. Tests: `lifecycle.test.ts` ("a reconnect while a silence is open"), `recovery.test.ts` (R13 and R04, both paths), `src/doctor/__tests__/doctorStore.test.ts` (the live view equals the batch analysis), `src/cli/__tests__/commands.test.ts` (the exit code of `analyze`). Not changed, because they are not the same shape: R10's late heartbeat (it is judged only while its connection is open, so it is never left open by a closing connection), and the findings that are a fact about the capture and never resolve (R01 status and type, R02, R03, R07 loops, R08, R09, R12, R15).


### Q13. An early stall becomes part of the rhythm the next one is judged by: decided and implemented

The limit is three times the 95th-percentile gap of the stream's own history. With about a dozen gaps of history, one 8 s stall became that percentile, so the same stall again (limit 24 s) was not reported; with about forty gaps it did not move.

**The owner's decision:** "Exclude gaps already classified as stalls from the baseline used to detect subsequent stalls. A previous failure must not teach the detector to tolerate the same failure again. Add a regression test with approximately 12 gaps, an 8-second stall, and another 8-second stall."

**Implemented:** the model keeps two sets of gap statistics: `gaps` (every gap that ended with a byte, which R07, R10's "no heartbeats seen" and R11 read) and `baseline` (the same without the stalls), which R05 and R13 judge by. "Classified as a stall" means the rule's own verdict at the time: the gap was longer than the limit that applied while it was open (3 x p95 or twice the heartbeat interval, never under 1 s; the declared longest silence; or 30 s before enough gaps were seen), computed by one shared function (`stallLimit`), so a gap of exactly the limit stays in the baseline and one a millisecond longer does not. Tests, `lifecycle.test.ts`: twelve gaps, an 8 s stall and another 8 s stall (both reported); the forty-gap variant; the edge at 3000 and 3001 ms; a slow stream's long gap under its own limit; the declared-silence edge; the default limit.

**The owner's second decision, on a stream that slows down for good:** "I approve controlled adaptive cadence rather than permanent exclusion or simple documentation. Implement a two-stage approach: 1. Exclude gaps classified as stalls from the healthy cadence baseline. 2. Recognise a sustained cadence shift only after three consecutive, reasonably consistent intervals around a new cadence. When confirmed, update the baseline, resolve the active stall episode while preserving its historical evidence, and emit an informational cadence-change observation. An explicitly configured `expected.maxSilenceMs` must remain authoritative. Never automatically learn a cadence that violates the user's declared expectation." Implemented (`stallLimit.ts`, `streamModel.ts`, `r05StallSilent.ts`): three consecutive stalls on one connection, none of them separated by a normal gap, each within 25% of their median (the edge inside), with none longer than a declared `expected.maxSilenceMs`, rebuild the baseline from those three gaps, keep the stall as resolved history (facts, numbers, evidence and count kept, plus one fact), and emit `cadence.changed:<kind>` (info: the old and the new rhythm, the three silences with evidence, "inferred from the stream's own intervals", not proof of the producer's intent). A reconnect starts the count again. Tests: `cadenceShift.test.ts` (a single stall, two, three consistent, sporadic, inconsistent, the 25% edge both sides, a declared silence overriding, its edge, a new stall after the change at 24000 and 24001 ms, other connection), `cadenceShiftProperty.test.ts` (live equals batch for random runs, evidence is real), `doctorStore.test.ts` (the live view), `commands.test.ts` (an adapted stream passes the gate at its new rhythm, a later stall fails it).

### Q15. Forged proxy tags (decided: the proxy rewrites them)

The proxy forwarded an upstream's `: sse-proxy hb up_idle=...` comment as it came, and the client labels any comment starting with `sse-proxy` as the proxy's, so an upstream (with diagnostics off or on) could make R13 report masking and R05 name the origin when the upstream was healthy. **Decision:** the proxy escapes or rewrites upstream comments in the reserved `sse-proxy` namespace before it adds its own tags, so an upstream cannot impersonate a proxy heartbeat, and a real proxy-in-the-loop test proves it.

- **Form chosen:** ` upstream:` is inserted right after the colon (`: sse-proxy hb up_idle=9 n=1` becomes `: upstream: sse-proxy hb up_idle=9 n=1`). It keeps the text readable and every byte of it, it is out of the namespace so nothing labels or parses it as the proxy's, it is applied once (a second proxy does not rewrite it again), and the line count does not change, so framing cannot break. Dropping the line was rejected (it would lose the upstream's bytes and hide the forgery from the user); a nonce in the tags was rejected (the Doctor would have to carry it, and a captured file could not be read without it).
- **What is matched:** `:`, up to 32 spaces or tabs, then `sse-proxy` in any letter case (the client itself labels only `:` + at most one space + lower case; the proxy is wider on purpose, since the namespace is reserved however it is spelled). Every line of a comment block, a comment inside an event, after a byte order mark, with LF, CR and CRLF, and across network chunks (a comment line is held back only while its first bytes could still be the namespace; everything else is forwarded at once; what is held at the end of the stream is released unchanged).
- **Tests:** `src/tests/reservedComments.test.ts` (the forms rewritten, the forms left alone byte for byte, every cut point, properties against the specification's parser and a line-by-line oracle, and that the framing the proxy's tracker sees is the parser's at every chunk end); `src/tests/streamProxy.test.ts` (the bytes the proxy writes, diagnostics on and off, with a comment split across two chunks while heartbeats are written); `src/fixtures/__tests__/proxyInTheLoop.test.ts` ("an upstream that writes comments shaped like the proxy's tags": a forging upstream through the real proxy, diagnostics on and off: every forged comment arrives labelled as the upstream's, the proxy's own ping, meta and heartbeats still read as the proxy's, `proxy.masking` and `stall.silent:origin` do not fire, and the forwarded bytes equal the upstream's log with exactly the forged lines rewritten, checked against a regular expression written separately from the proxy's code; the same forger read directly still fires `proxy.masking`, which shows the proxy is what closes the hole; an honest upstream's comments pass byte for byte).
- **Still true:** the tags are not authenticated against something between the proxy and the browser. A comparison of the forwarded bytes with the upstream's log must now account for the rewritten lines (ten bytes each).

### h06 `?bare=1`: the client keeps reconnecting (decided: keep it; the test is bounded and pins the finding)

`h06-comments-only?bare=1` sends comments and closes without an event. The client treats a close without the end event as a drop and comes back, every time. **Decision:** keep the reconnect; make the test bounded and verify the loop finding explicitly. (`f04-late-heartbeat` is approved and kept; its twin is `h06-comments-only`.)

- **Why a retry limit cannot bound it:** the client's `maxRetries` counts consecutive failed attempts and starts again each time a connection opens. This server always lets the connection open, so the loop has no end of its own. The test helper `observeUrl` now takes `stopAfterConnections` (the client is stopped as soon as that many connections have ended and it is about to come back, so every connection in the server's log was ended by the server) and `timeoutMs` (default 15 s; the client is stopped in a `finally` whether the run ends or times out).
- **What the loop is reported as:** `reconnect.loop`, **error** ("Reconnecting without getting any data"), because no event arrived on any connection. With 5 connections at scale 0.1 its first fact says "5 connections were opened within ..." (connections 0 to 4), its evidence is the five `connect` records (same sequence numbers, times and connection numbers), and the run of five reconnects is anchored on the first and last `reconnect` records. `reconnect.duration-pattern` (warning) may also appear, because this server closes every connection after the same time; the test allows it and does not require it (it depends on timer jitter). Nothing else fires: no `stall.silent` (the comments keep the connection alive), no heartbeat finding, no slow start, no violation.
- **Contract:** unchanged. `expectedFindings` and `forbiddenFindings` of `h06-comments-only` describe the default stream, which ends with the end event and must be silent; `?bare=1` is a variant, and the fixture's description now says so.
- **Tests:** `src/fixtures/__tests__/fixturesMore.test.ts`, block "h06-comments-only?bare=1: the client comes back every time": (1) `maxRetries: 1` does not stop the loop, a count does; (2) five connections, each ended by the server with three comments and no data frame, the finding's key, severity, text, evidence and counts agree with the server's log, nothing else fires; (3) the twin (the same route without `?bare=1`) ends on its first connection, has no `reconnect.loop`, and the rule was evaluated. Checked once by breaking the rule (severity `warning`) and the fixture (end event always sent): the test fails in both.

## Not covered

- A real screen reader, Safari and mobile; a real CDN or reverse proxy buffering; the Vercel runtime; long soak runs; real network faults; CPU overhead on a quiet machine (the "under 2% CPU at 500 events/s" target is still **not demonstrated**, see the README).
- Two of fifteen rules have no fixture stream that makes them fire (R13, which only the proxy-in-the-loop test fires, and R15, a clock jump a server cannot produce); the reasons are in `src/core/diagnostics/__tests__/ruleCoverage.test.ts`.
- R07's coefficient-of-variation edge of exactly 0.03 cannot be built from whole-millisecond lifetimes, so `<` against `<=` there is untestable; it is pinned to within 1 ms.
- E1 covers the Doctor's exports (each shareable kind, both curl shells) and every command and format of the command line, with the planted secrets in these places: Authorization, Cookie, API-key and Proxy-Authorization headers, a Set-Cookie response header, URL userinfo, `?token=` and `?api_key=` query values, a JWT in a payload and in an event id, a nested `password` key, a `token` inside a list, an `api_key=` in a comment, and a JWT split across two chunks. It does **not** cover the v1 app's own JSON/CSV exports (never redacted, plan question Q2), or secrets that no rule can recognise: a random token in free text is flagged and kept, and a low-entropy secret sentence is neither removed nor flagged (both pinned by tests).
